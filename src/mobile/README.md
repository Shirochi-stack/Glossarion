# Glossarion Mobile (Android + iOS)

Flet 1.0.3 app (Flutter Material 3 UI + embedded CPython 3.13) that runs the
Glossarion backend in-process on phones and tablets. Device builds happen in
GitHub Actions (`.github/workflows/build-mobile.yml`); locally you only need
Python to run the app in a desktop window and to run the host tests.

Status: every milestone of the plan (U0-U9) has shipped: the chat-first UI from
`docs/UI_SPEC.md` (chat, Library + Reader, Glossaries, Tools incl. Manga, Settings, Accounts,
Jobs), tablet layouts and accessibility, the experimental browser routes and About › Updates.
The app is **never published** (owner's rule, see "Releases"); CI builds a debug-signed APK and
an unsigned IPA on manual dispatch only, as downloadable run artifacts. The U0 device-spike screen
(`app/glossarion_mobile/ui/spike.py`) stays reachable as Logs & diagnostics › Device checks.

## Local development (Windows/macOS/Linux)

```bash
cd src/mobile
python -m venv .venv                       # gitignored; Python 3.12+ is fine for desktop dev
.venv/Scripts/python -m pip install flet==1.0.3 flet-secure-storage==1.0.3 \
    flet-permission-handler==1.0.3 pytest  # (macOS/Linux: .venv/bin/python)
# once uv.lock exists: uv sync   (Python 3.13, the exact device pins)

python tools/prepare_assets.py             # tiktoken cache + self-test EPUB into app/assets/
flet run                                   # desktop window; backend imported from the repo src/
python app/main.py                         # same, without the flet CLI
```

* The backend is found in this order: `GLOSSARION_BACKEND_DIR` → the repo `src/`
  (when `app/main.py`'s `parents[2]` contains `TransateKRtoEN.py`) → `app/backend/`.
  Set `GLOSSARION_BACKEND_DIR=src/mobile/app/backend` to test the collected bundle.
* Storage: `flet run` uses `.flet/storage/{data,cache,temp}`; `python app/main.py`
  without `FLET_APP_STORAGE_*` falls back to `src/mobile/storage/` (keep it out of git).
* Desktop dev behaves like the device (`GLOSSARION_MOBILE=1`, no processes) except that
  the native extension is replaced by a stub (no foreground service, notifications,
  share intake or background tasks) and `~` on Windows still expands to `%USERPROFILE%`.
* Flet runs sync handlers on the asyncio loop: UI handlers are `async` and never block;
  blocking work goes to a thread. Built apps hard-exit (no `atexit`), so state is
  flushed on lifecycle `INACTIVE/HIDE/PAUSE`.

### Host checks

The security pins require Pillow 12.3.0 and cryptography 50.0.2. The PyPI/Flet indexes have
no Android builds of either (and no iOS cryptography 50.0.2), so CI builds them itself
(`.github/workflows/mobile-wheels.yml`, `ci/wheels/`, `.github/actions/mobile-wheelhouse`):
`check_mobile_wheels.py --wheelhouse-plan` checks the index side plus the planned wheels, and
the build jobs verify the built wheels (`--verify-installed`: OpenSSL version, undefined
symbols). The first all-green Build Mobile with these wheels was run 37728461336 (96da1ec6).
Do not downgrade these pins or bypass the wheel check to make a release.

The wheel check reads a pypi.flet.dev wheel's dependencies from the wheel's own METADATA (HTTP
range reads of the zip's tail; the index serves no PEP 658 metadata), because flet's builds can
declare more than the PyPI release: llama-cpp-python's Android wheels add `flet-libcpp-shared`.
When the METADATA cannot be read it falls back to PyPI's JSON.

Untrusted Pillow image reads use `safe_image.open_image`, which restricts
parsers before opening headers. EPS, JPEG2000 and McIdas input is rejected;
ordinary PNG/JPEG/WebP/GIF/BMP/TIFF inputs and Pillow's pixel-bomb guard remain
supported. This protection complements the package updates.

### On-device engine (llama.cpp)

Model manager › On-device runs GGUF models inside the app through **llama-cpp-python 0.3.32**
(`[tool.flet.android]` / `[tool.flet.ios]` dependencies; device-only, so the host `uv sync` never
builds its sdist). pypi.flet.dev has cp313 wheels of that version for all five targets (flet-dev/
mobile-forge `recipes/llama-cpp-python`, build tag 2), but they are built without llava/mtmd, so no
model could read an image. CI therefore builds the same version itself from forge's recipe with
`LLAVA_BUILD=ON` and `MTMD_VIDEO=OFF` (`ci/wheels/recipes/llama-cpp-python`, a `[[wheel]]` in
`wheelhouse.toml`, build tag 1000 outranks the index; mobile-wheels.yml builds and caches it like
cryptography). The wheels are CPU-only (`GGML_NATIVE=OFF`, no Metal / Vulkan / OpenMP) and pure
ctypes over five libraries in `llama_cpp/lib`: libggml-base, libggml-cpu, libggml, libllama and
libmtmd (the image encoder of vision models).

* **CPU variants (Android arm64).** One armv8.0 build would leave out the int8 dot-product (`dotprod`,
  Cortex-A55/A75 and later, Snapdragon 845+) and matrix-multiply (`i8mm`, Cortex-A510/A710/X2 and
  later, Snapdragon 8 Gen 1+) instructions that make Q4/Q8 matmuls several times faster, but a build
  that needs them would crash (SIGILL) on the Cortex-A53 phones that `min_sdk_version = 26` still
  allows. The arm64 wheel is therefore built with `GGML_BACKEND_DL=ON` + `GGML_CPU_ALL_VARIANTS=ON`:
  libggml-cpu is replaced by four CPU backends, `libggml-cpu-android_armv8.0_1` (baseline),
  `_armv8.2_1` (dotprod), `_armv8.2_2` (dotprod + fp16) and `_armv8.6_1` (dotprod + fp16 + i8mm), and
  the patched loader (`patches/mobile.patch`, 7.) asks each for its `ggml_backend_score()` (a feature
  probe built without the variant's flags; 0 when the CPU lacks one) and registers the best one,
  loading it by bare soname from the APK's jniLibs (ggml's own `ggml_backend_load_all()` only looks in
  the executable's directory and the cwd). No SVE / SVE2 / SME variants: every such phone core also has
  i8mm, and ggml's SVE repack kernels want 256-bit vectors (phones have 128). The engine card shows the
  CPU line of the registered backend (`DOTPROD = 1`, `MATMUL_INT8 = 1`, ...) and `(CPU variant
  android_armv8.6_1)`; `LLAMA_CPP_CPU_VARIANT=<variant>` in the environment tries one first (ggml still
  refuses a variant the CPU cannot run). Cost: each variant is about 0.8 MB, so the arm64 APK grows
  by about 2.4 MB. Measured on GitHub's arm64 runner (Neoverse N2, 4 threads, Qwen2.5 0.5B; the
  `cpu_check` job, see below), armv8.0 baseline -> best variant: Q4_0 prompt 89 -> 619 tok/s and
  generation 48 -> 94 tok/s; Q4_K_M prompt 83 -> 153 tok/s and generation 45 -> 68 tok/s.
  x86_64 (emulator, Chromebooks) keeps the single built-in libggml-cpu. iOS keeps it too: the floor is
  iOS 13 (A9 / A10 / A11 / A12 iPhones have no dotprod, A13+ do, i8mm from A15), dylibs in an app are
  framework-relocated and code-signed, and llama.cpp's Apple variant list starts at dotprod; Metal
  (phase 2) is the larger iOS gain.
  `wheels.py verify-native` / `verify-site-packages` expect exactly these eight arm64 libraries and scan
  their code: SDOT/UDOT, SMMLA/USDOT, SVE and SME instructions may appear only in the variants that
  promise them, and each variant must contain its own (proof that its `-march` took effect).
  `mobile-wheels.yml` dispatched with `cpu_check=true` builds the same set on a Linux arm64 runner and
  runs `ci/wheels/cpu_variants_check.py`: the variant picked natively, tokens/s per forced variant, and
  under `qemu-aarch64 -cpu cortex-a53 / cortex-a76` that older cores get the baseline / dotprod variant
  and generate without SIGILL.

* Size: about 4 MB of native libraries per ABI, plus jinja2, MarkupSafe and diskcache (about 1 MB
  of Python, resolved by pip). Android also installs `flet-libcpp-shared` (`libc++_shared.so`,
  which must exist exactly once in the APK: Gradle merges jniLibs).
* `wheels.py verify-native` checks the built wheels and, after every `flet build`, `wheels.py
  verify-site-packages --platform <p> --package llama-cpp-python build/site-packages` checks what
  pip installed, both against the same profile: the pinned version and build >= 1000, exactly the
  five libraries, then per arch the ELF machine, 16 KB LOAD alignment, NEEDED (siblings,
  libc++_shared, libc/libm/libdl/liblog) and every strong import resolved by a sibling,
  libc++_shared or the NDK API-24 stubs (Android); the slice's CPU and platform, minos <= 13.0
  (14.0 on the arm64 simulator), only sibling and `/usr/lib` dylibs and no DYNAMIC_LOOKUP binds (iOS).
* The app's `ENGINE_VERSION` equals the pin (a host test checks it); the smoke suite's
  `llama_engine` check imports `llama_cpp`, loads the libraries and libmtmd on the emulator and the
  iOS simulator.
* Models are GGUF files in `GLOSSARION_MODELS_DIR` (`<data>/models`, app-internal; excluded from
  iCloud backup on iOS; on Android a model over Auto Backup's 25 MB quota just stops the app's backup).
* RAM: a model needs roughly its file size × 1.15 + the KV cache + 400 MB. Android refuses a load
  above the phone's total RAM and asks first above the available RAM; iOS refuses above half the
  RAM (unsigned / AltStore IPAs cannot carry the increased-memory-limit entitlement). Qwen3.5 4B
  wants about 4 GB free and 9B about 8 GB. Welcome page 1 ("Run on this phone") and the Model manager
  show this check as a hint per preset (✓ fits, ⚠ tight on free RAM, ✕ too big).
* **Vision.** Qwen3.5 is natively multimodal: the default presets carry their repository's
  `mmproj-F16.gguf` (205-918 MB), and any repository with an `mmproj-*.gguf` gets its projector in
  the same tap (F16, else BF16, Q8_0, F32), downloaded like the model (resume, sha256) as
  `<stem>.mmproj.gguf` and recorded on the model in `models.json`. Such models say "Reads images"; the
  in-app endpoint then takes OpenAI `image_url` parts with `data:` URLs (no remote URLs), decodes
  them with `safe_image.open_image`, scales the longest side to 896 px, re-encodes JPEG and runs
  llama-cpp-python's `MTMDChatHandler` (the model's own chat template, thinking off). The projector
  loads with the first image only and the RAM gate checks again with it added. Text-only models keep
  the 400 "no vision support". The chat's Vision mode and image jobs reach it through
  `UnifiedClient.send_image` and the `local/` route like any other vision model.

## Building

Device builds need Flutter, a JDK 17 and the Android SDK (Android) or Xcode (iOS);
CI installs them. `tools/build.py` wraps `flet build` and injects the version:

```bash
python tools/build.py prepare        # collect backend + assets + verify
python tools/build.py apk            # per-ABI APKs (arm64-v8a, x86_64); debug-signed without a keystore
python tools/build.py aab            # Play bundle (needs the release keystore)
python tools/build.py ipa            # macOS: unsigned unless signing args follow `--`
python tools/build.py apk -- -vv     # extra flet build args after --
python tools/build.py apk --legacy-packaging   # compressed native libraries (see "APK size")
python tools/build.py size           # where the APK bytes go (ci/apk_size_report.py on build/apk/*.apk)
python tools/build.py ui-tests --device-id emulator-5554   # `flet test android` (tests/, see below)
```

Version: `--build-version` = `APP_VERSION` from `src/app_version.py`, `--build-number`
= `M*1_000_000 + m*10_000 + p*100` (9.13.6 → 9130600). Never edit the version in
`pyproject.toml`.

### CI (`.github/workflows/build-mobile.yml`)

Triggers: **manual dispatch only** (plus `workflow_call`, which nothing uses: `build-all.yml`
does not build mobile). There is no push or tag trigger. Dispatch inputs: `targets`
(all/android/ios), `emulator_smoke`, `ios_simulator_smoke`, `ui_tests` and `llama_suite`
(auto/on/off) and `android_legacy_packaging` (the APK size experiment).

Jobs: `prepare` (version, wheel plan, backend bundle, host tests, offline E2E) →
`wheels-android` / `wheels-ios` (the self-built cryptography/Pillow wheels) → `android`
(APKs per ABI + size report) → `android-smoke` (x86_64 API 35 emulator: READY markers, the
self-test deep link, then the offline E2E suite; blocking) → `ios` (unsigned IPA) →
`ios-signed` (only with the Apple secrets) → the optional device suites below. There is no
release job: the workflow never publishes (see "Releases").

Artifacts: `X_Glossarion-Android-APK`, `Z_Glossarion-Android-AAB`,
`X_Glossarion-iOS-Unsigned` (AltStore/SideStore), `X_Glossarion-iOS-Signed`,
`Z_Glossarion-iOS-Simulator` (7 days); internal: `mobile-prepared`, `mobile-backend-report`,
`mobile-apk-size-report`, `mobile-smoke-logs-*`, `mobile-ui-test-logs`.
`tests_host/test_ci_release.py` (also run by `python-app.yml` on every push) pins the triggers,
the no-publishing rule (no release job, no publish input, no write permission), the 7-day
artifact retention and the suite policies.

#### APK size

Measured from the CI artifacts (`gh api .../actions/runs/<id>/artifacts`):

| Run (commit) | arm64-v8a APK | x86_64 APK | Unsigned IPA |
|---|---|---|---|
| 37410230047 (e28e3a0f, U5) | 248.9 MB | 276.2 MB | 138.0 MB |
| 37468750016 (5befbc80, U6) | 249.5 MB | 276.8 MB | 138.6 MB |
| 37512537733 (8ecb95ed, U7) | 263.9 MB | 294.8 MB | 149.1 MB |
| 37697523575 (1cd68178, U8 + own wheels) | 284.4 MB | 315.3 MB | 169.2 MB |

(decimal MB; APKs from the Android build log, IPAs from the artifact sizes).

Where the bytes go: Flet 1.0.3 / serious_python store every native library uncompressed and
page-aligned (`lib/<abi>/*.so`, modern packaging) and ship the Python code as STORED zips
(`stdlib.zip`, `sitepackages.zip`, the app), so nothing in the APK is compressed. The heavy
packages (OpenCV, onnxruntime, PyMuPDF, NumPy) are all used (manga, PDF); `scipy` is not in the
lock. What U9 changed:

* `[tool.flet.cleanup] package_files` drops trees nothing imports at run time
  (`onnxruntime/transformers/models`, `numpy/f2py`, `pymupdf/mupdf-devel`), a few MB of the
  ABI-common zips. `split-per-abi` and `target_arch = [arm64-v8a, x86_64]` were already set.
* Every Android build writes a size report to its job summary and the
  `mobile-apk-size-report` artifact (`ci/apk_size_report.py`): totals per category, the largest
  native libraries and Python packages, and the APK size with compressed native libraries.
* `--android-legacy-packaging` (dispatch input `android_legacy_packaging`, or
  `tools/build.py apk --legacy-packaging`) compresses the native libraries: a much smaller
  download, but Android then also keeps an extracted copy (a bigger install) and loads the
  libraries from disk. It stays off by default until a run's size report shows the numbers;
  turning it on for good is `legacy_packaging = true` under `[tool.flet.android]`.

### Releases (never)

Mobile builds are never published (owner's decision, 2026-10-09: the publishing part of the
workflow was removed). `build-mobile.yml` has no release job, no publish input and only
`contents: read`, so neither a manual run nor a `workflow_call` can create or change a GitHub
release, and no other workflow uploads a mobile file. To get a build, download the APK/IPA
artifact from the Build Mobile run (Actions › Build Mobile › the run › Artifacts:
`X_Glossarion-Android-APK`, `X_Glossarion-iOS-Unsigned`, …); artifacts are kept 7 days.

### In-app updates (About › Updates)

The app runs the desktop's release check (`src/update_core.py`, moved out of
`update_manager.UpdateManager`: the 30-minute cache, skipped versions, `/releases/latest`) on
the mobile `config.json`, so `auto_update_check`, `last_update_check_time` and
`skipped_versions` mean the same on both. Check now · Check on startup · Skip this version ·
release notes · "Download APK" (Android: the APK for the device's ABI, release-signed first,
opened in the browser) or the IPA links (iOS) when a release has such a file. Mobile builds are
never published, so releases have no mobile files; the page then says so and links the release
page. Nothing is installed by the app. The startup check runs once per session, only on a
phone/tablet, never while a self-test runs or under `flet test` (`GLOSSARION_UPDATE_CHECK=0`
turns it off), and only speaks up when a newer release has a file for the device.

### iOS Share Extension (not shipped)

The plan's optional iOS Share Extension is skipped, recorded here: it would be a second
Xcode target (an app extension with its own bundle id `com.glossarion.app.share`) that Flet
1.0.3's build template cannot add without patching the generated Xcode project after
`flet build` on every CI run, and it needs an App Group shared with the app, i.e. its own
provisioning profile for the signed IPA and App-Group re-signing support in AltStore/SideStore
for the unsigned one. iOS already reaches Glossarion from the share sheet's "Open in…" /
Files "Share › Glossarion" through the document types in `[tool.flet.ios.info]`
(`CFBundleDocumentTypes`, `LSSupportsOpeningDocumentsInPlace`), which the IntentRouter
handles; shared *text* goes through the clipboard. Manga page images arrive the same way: an
"Image" document type (`public.image`, role Viewer, rank Alternate) offers Glossarion for
pictures, and the IntentRouter shows "Manga translator" for them (Android "Open with" lists the
app for `image/*` too).

## Signing

All secrets are optional; without them CI ships a debug-signed APK and an unsigned IPA.

| Secret / variable | What it is |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 glossarion-release.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | key alias (e.g. `glossarion`) |
| `ANDROID_KEY_PASSWORD` | key password (defaults to the keystore password) |
| `IOS_DIST_CERT_P12_BASE64` | Apple distribution certificate + key, `.p12`, base64 |
| `IOS_DIST_CERT_PASSWORD` | `.p12` password |
| `IOS_PROVISIONING_PROFILE_BASE64` | provisioning profile for `com.glossarion.app`, base64 |
| `IOS_TEAM_ID` | Apple team id |
| variable `IOS_EXPORT_METHOD` | `release-testing` (default), `app-store-connect`, `debugging`, … |
| variable `IOS_SIGNING_CERTIFICATE` | optional certificate name override |

Create the Android key once and keep it forever (a new key cannot update installed apps):

```bash
keytool -genkeypair -v -keystore glossarion-release.jks -alias glossarion \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w0 glossarion-release.jks > keystore.b64   # paste into ANDROID_KEYSTORE_BASE64
```

Locally, `flet build` reads `FLET_ANDROID_SIGNING_KEY_STORE`,
`FLET_ANDROID_SIGNING_KEY_STORE_PASSWORD`, `FLET_ANDROID_SIGNING_KEY_PASSWORD` and
`FLET_ANDROID_SIGNING_KEY_ALIAS`.

#### Signed iOS (`ios-signed`)

With `IOS_DIST_CERT_P12_BASE64`, `IOS_DIST_CERT_PASSWORD`, `IOS_PROVISIONING_PROFILE_BASE64`
and `IOS_TEAM_ID` set, `ios-signed` builds a second, signed IPA next to the unsigned one:

1. the `.p12` goes into a temporary keychain (random password, 6 h lock, removed at the end);
2. the profile is installed under its UUID; a warning flags an `application-identifier`
   other than `<team>.com.glossarion.app` (or a wildcard);
3. the export method is `IOS_EXPORT_METHOD` (default `release-testing`, i.e. ad hoc: installs
   on the devices in the profile) with "Apple Distribution", or "Apple Development" for
   `debugging` / `development`; `IOS_SIGNING_CERTIFICATE` overrides the certificate name;
4. `flet build ipa --ios-team-id … --ios-signing-certificate … --ios-provisioning-profile <uuid>
   --ios-export-method …`, then `ci/verify_ipa.py --expect-signed` (embedded profile + code
   signature) and the artifact `X_Glossarion-iOS-Signed`.

A distribution certificate: Keychain Access › Certificate Assistant › Request a Certificate
from a Certificate Authority, upload the CSR at developer.apple.com › Certificates (Apple
Distribution), install it, export certificate + key as `.p12`, then `base64 -i dist.p12`. The
profile: Profiles › Ad Hoc (or App Store) for the App ID `com.glossarion.app` with the
devices, download, `base64 -i Glossarion.mobileprovision`. The unsigned IPA is the one to
sideload (AltStore/SideStore sign it with the user's own Apple ID).

## Runtime contract (runtime_bootstrap.bootstrap)

Runs before Flet and before any backend import; idempotent (Android may restart
the Dart VM while Python keeps running).

* Paths: `<data>` = `FLET_APP_STORAGE_DATA` (also the cwd), `<cache>` =
  `FLET_APP_STORAGE_CACHE`, `<temp>` = `FLET_APP_STORAGE_TEMP`, `<docs>` = iOS
  `Documents/Glossarion` (Files-visible; from the HOME captured before the override)
  or `<data>` elsewhere.
* Env: `GLOSSARION_MOBILE=1`, `GLOSSARION_NO_PROCESSES=1`,
  `GLOSSARION_HEADLESS_KEY_MANAGER=1`, `GLOSSARION_APP_DIR`/`GLOSSARION_DATA_DIR=<data>`,
  `CONFIG_FILE=<data>/config.json`, `HOME=<data>/home`, `OUTPUT_DIRECTORY=<docs>/Output`,
  `GLOSSARION_LIBRARY_DIR=<docs>/Library`, `GLOSSARION_LOG_DIR=<data>/logs`,
  `GLOSSARION_MODELS_DIR=<data>/models` (on-device GGUF models + `models.json`, created on demand),
  `GLOSSARION_MODEL_CATALOG_CACHE=<cache>/model_catalog_cache.json`, `XDG_CACHE_HOME=<cache>`,
  `TMPDIR/TEMP/TMP=<temp>`, `TIKTOKEN_CACHE_DIR=<cache>/tiktoken` (seeded from
  `assets/tiktoken`, checked against its `MANIFEST.toml`), `SSL_CERT_FILE` =
  `REQUESTS_CA_BUNDLE` = certifi, `GLOSSARION_HTTP_LOG=0`,
  `GLOSSARION_OAUTH_RETURN_URL=glossarion://app/oauth/return`,
  `USE_ASYNC_CHAPTER_EXTRACTION=0`, `PDF_EXTRACTION_WORKERS=1`, `QA_USE_THREAD_EXECUTOR=1`,
  `GRPC_DNS_RESOLVER=native` (the Android grpcio build's c-ares finds no DNS servers on Android 8+);
  bookkeeping: `GLOSSARION_PLATFORM`, `GLOSSARION_ORIGINAL_HOME`.
* `threading.stack_size(16 MiB)` for every new thread. Never call
  `threading.stack_size()` without an argument: that resets it to the default
  (use `runtime_bootstrap.current_thread_stack_size()`).
* Logs: `<data>/logs/run.log` (2 MB × 5), `crash.log` (faulthandler; a non-empty tail
  after the last `=== boot` header means the previous run crashed), `selftest-last.json`;
  Flet also writes `<cache>/console.log`.
* `webbrowser.open()` → preferred `glossarion-inapp` controller → UrlLauncher
  `IN_APP_BROWSER_VIEW` (Custom Tabs / SFSafariViewController), so the desktop OAuth
  loopback flows run unchanged.

### Device log markers

Printed to `sys.stderr`, which Flet routes to logcat tag `flet.python` (Android) and
os_log (iOS) plus `console.log`. (`sys.__stderr__` is fd 2 = `/dev/null` on Android.)

| Marker | When |
|---|---|
| `GLOSSARION_BOOT {json}` | end of bootstrap |
| `GLOSSARION_READY` | the first page is built |
| `GLOSSARION_BACKEND_READY modules=<n> secs=<s>` | warm import finished (`n` = backend modules loaded) |
| `GLOSSARION_BACKEND_FAIL {json}` | warm import failed |
| `GLOSSARION_SELFTEST_START {json}` | self-test started (suite, source) |
| `GLOSSARION_SELFTEST PASS {json}` / `FAIL {json}` | self-test finished (deep link or button) |
| `GLOSSARION_SPIKE …` | U0 spike results (FGS ticks every 60 s, events) |
| `GLOSSARION_LLAMA {json}` | the `llama` suite's result (model, sha256_ok, load_s, tokens, tok_s, system_info) |
| `GLOSSARION_LLAMA_VISION {json}` | the `llama` suite's vision check (model, projector, sha256_ok, seconds, text, prompt_tokens, projector_loaded, red) |

```bash
adb logcat -s flet.python
adb shell am start -W -a android.intent.action.VIEW \
  -d "glossarion://app/__selftest__?suite=smoke" com.glossarion.app
# iOS simulator: openurl stops at an "Open in ...?" alert; launch with the env trigger instead
SIMCTL_CHILD_GLOSSARION_CI_SELFTEST=smoke xcrun simctl launch --console-pty booted com.glossarion.app
```

Routes: `ui/router.py` whitelists every route of UI_SPEC (opaque ids only, never paths or
text); deep links `glossarion://app/<route>` go through the same whitelist. Flet hands
Python the path form of a deep link (`glossarion://app/x?y` → `/x?y`); everything
else (content:/file: paths from Open-with, foreign links) is ignored and recorded.
On iOS a cold-start `glossarion://app/...` link is swallowed by receive_sharing_intent's
UIScene hook; the extension re-delivers it as a shared item (`kind="url"`,
`source="launch"`), which the spike routes through the same whitelist (de-duplicated
against `page.route`).
